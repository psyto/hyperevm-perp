VERDICT: CHANGES

1. **High — non-final statuses can release the one-order gate.** `track()` treats every value other than `unknownOid`, `open`, or a locally prefixed error as final ([orders.py:81-90](recorder/orders.py:81)). The documented status set includes `triggered`, which is not terminal; an unknown/future API value is also accepted. The script then calls `acknowledge`, clearing `pendingCloid` ([orders.py:169-171](recorder/orders.py:169)), permitting another CoreWriter order while the first may still execute. Accept only `status == "order"` with a strict terminal allowlist, and fail closed on every other response. Also validate returned `cloid`, coin, side, limit, and size.

2. **High — `run` does not stop on unexpected economics and can leave/open a Core position.** Despite its docstring, it continues after any accepted “final” result. A supposedly margin-rejected or miss order that fills is acknowledged and the next buy is sent; 20 unexpected margin fills can accumulate a long. Fill pairs assume equal complete fills but never verify per-order size or that the position returns to zero ([orders.py:158-171](recorder/orders.py:158)). Before every send, assert the required starting position/collateral; after each result, require the expected outcome and expected position delta. On any mismatch, write evidence and leave `pendingCloid` set for manual handling.

3. **Medium — receipt polling has no finality/recovery discipline.** `send()` accepts the first receipt with no canonical-block check or confirmation ([orders.py:141-149](recorder/orders.py:141)). A reorg or process/network failure after broadcast can leave a Core action pending with no JSONL row; a failure after acknowledgement broadcast can leave its recording ambiguous. Persist the tx hash before polling, record block hash/log index, use a suitable confirmation/canonicality policy, and provide a resume/reconciliation path that queries contract `pendingCloid`, order status, position, and open orders before sending anything else.

4. **Medium — timing data is observation latency, not reliably CoreWriter timing.** `changes` is sampled every 200 ms relative to local `receipt_at`; it includes RPC latency, API indexing/cache behavior, polling quantization, local clock skew/NTP jumps, and errors ([orders.py:72-99](recorder/orders.py:72)). `block_ts` is only whole seconds, while `receipt_at` is local. The Core timestamps are useful but do not recover sub-second EVM-block timing. Publish these as “first observed by this client/API” distributions, retain raw responses and request/response times, use a monotonic clock for elapsed time, and analyze `core_status_ts - core_order_ts` separately from client observation latency. Do not compare ordered blocks of 20 outcomes as independent samples: account state, API load, time of day, and sequence confound them.

5. **Medium — `watch` is neither lossless nor deduplicated/reorg-safe.** It has no durable cursor, block hash, log index, or dedupe key; restart/default-head behavior can miss prior events, while overlapping `from_block` runs duplicate them. It advances its cursor after a non-finalized head and does not retry RPC failures ([orders.py:114-131](recorder/orders.py:114)). Processing logs serially means a later event’s `receipt_at` may be tens of seconds after its block if an earlier `track()` waits, making watch timing invalid for those rows.

6. **Medium — polling is likely to hit rate limits and fail in unsafe-to-resume states.** Receipt polling at 10 RPC/s ([orders.py:141-145](recorder/orders.py:141)) alone can exceed the documented 100 EVM-RPC requests/minute; watch’s head-plus-logs cycle can also exceed it. `orderStatus` polling adds 5 requests/s, and there is no backoff/retry. A rate-limit exception in `send()` aborts after the transaction may already be broadcast. Hyperliquid documents a 100 RPC/minute limit, 1,200 REST weight/minute, and weight 2 for `orderStatus`/`clearinghouseState`; it also recommends WebSockets for low latency. [Rate limits](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits) Add bounded backoff, request budgeting, and durable recovery before fund-moving runs.

7. **Low — no direct key disclosure in output, but the raw private key is exposed to the child process environment.** The key is not placed in argv, JSONL, or normal output ([orders.py:134-140](recorder/orders.py:134)), which is good. However, `ETH_PRIVATE_KEY` is visible to processes able to inspect the `cast` process environment, and file permissions are not checked. Use a dedicated disposable testnet key, restrictive key-file permissions, and avoid running alongside untrusted same-user processes.

Hyperliquid explicitly documents that CoreWriter actions are delayed and appear first as enqueue then execution, reinforcing the need to fail closed on uncertain state. [CoreWriter documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore)
